# 源码阅读拆解

## 概述

从不熟悉的代码库中提取可理解的知识，而不是"读一遍就忘"。

**核心原则：像剥洋葱一样读代码——从外到内、层层深入，每层只关注一个核心问题。**

---

## 铁律

```
无明确目标，不开始阅读。
先整体后细节，先链路后分支。
每遍只问一个问题，答清楚再进下一层。
```

---

## 何时使用

**触发条件：**
- 用户说"帮我拆解这个项目"、"分析这个源码"、"这个库是怎么实现的"
- 接了一个新仓库，需要迅速理解项目结构
- 想学习某个开源项目的设计模式
- 需要看懂别人的代码后再做修改
- 关键词触发：源码分析、代码拆解、源码阅读、源码导读、理解项目、项目架构、read the code、understand the codebase

**不要用：**
- 只需要找一个特定函数或变量 → 用 Grep/Glob 直接搜索
- 自己的代码且已经熟悉 → 直接改
- 纯配置文件的修改 → 读配置即可

---

## 清单

你必须为每一项创建 TodoWrite 任务，按顺序完成：

1. **明确目标** — 确认用户要什么、当前水平如何、最终交付什么
2. **第一遍：鸟瞰** — 这是什么项目？解决什么问题？怎么跑起来？
3. **第二遍：骨架** — 目录结构、模块关系、核心数据结构
4. **第三遍：主链路** — 追踪一条完整执行路径，从入口到出口
5. **第四遍：深度拆解** — 每个关键模块六维分析
6. **第五遍：输出** — 生成分层文档（概览 + 深度 + 实战）
7. **自检** — 检查猜测、遗漏、矛盾

## 第一步：明确目标

在打开任何文件之前，和用户确认三件事：

### 1. 用户要什么？

```
你想从这个项目中获得什么？
A. 理解整体架构和设计思想（→ 侧重模块关系、设计模式、架构决策）
B. 复用某个功能或模块（→ 侧重具体实现、API 接口、数据流）
C. 学习特定技术或技巧（→ 侧重核心算法、巧妙实现、工程技巧）
D. 要做二次开发或修改（→ 侧重扩展点、修改影响面、代码约定）
```

### 2. 用户什么水平？

```
对这个技术栈的熟悉程度？
A. 完全新手 → 每个概念都要解释，多打比方
B. 了解概念但没读过源码 → 重点讲设计思路和实现细节
C. 有经验但没读过这个项目 → 重点讲这个项目的独特设计
```

### 3. 最终交付什么？

```
你希望我输出什么？
A. 一篇快速概览（5 分钟读完）
B. 一份完整拆解文档（包含架构、链路、设计模式）
C. 一份带案例的教学文档（包含可执行的练习）
D. 一份源码导读（逐文件标注关键行号）
```

**没有明确答案，不要继续。**

## 第二遍：鸟瞰（这是什么？）

**目标：搞清楚这个项目"是什么"、"解决什么问题"、"怎么跑起来"。**

按优先级看这三个东西：

```
1. README.md / 项目官网
   → 项目叫什么、干什么、怎么安装
   → 跳过营销话术，抓核心功能描述
   → 如果 README 里有架构图，仔细看

2. package.json / Cargo.toml / go.mod
   → 项目名称、版本、依赖列表
   → scripts 命令 → 直接告诉你入口、构建、测试怎么跑
   → 依赖列表 → 看出技术栈和复杂度

3. 入口文件
   → package.json 的 main/bin 字段 / 项目根目录的 index 文件
   → 从这里知道"程序第一行执行的是什么"
```

**这遍的输出：**

```
用一段话说清楚：
- 这个项目是什么？（一句话）
- 它解决什么问题？（用户场景）
- 怎么跑起来？（安装+运行命令）
- 技术栈是什么？（语言、框架、关键依赖）
```

**红线：**
- 这遍不要深入任何源码文件
- 这遍不要追踪函数调用
- 这遍只回答"是什么"，不回答"怎么做"

## 第三遍：骨架（怎么组织的？）

**目标：画出模块地图，知道每个目录/文件负责什么。**

```
方法：
1. 列出顶层目录结构
2. 对每个目录，看 1-2 个代表性文件，标注职责
3. 画出模块依赖关系（谁 import 了谁）
```

**输出格式：**

```
src/
  cli.ts        → 命令路由，接收用户输入，分发到子模块
  add.ts        → 核心安装逻辑，最复杂（~2000 行）
  git.ts        → Git 操作封装（clone/pull/fetch）
  agents.ts     → 50+ 代理配置注册表
  types.ts      → 全局类型定义

模块依赖关系：
  cli.ts → add.ts → git.ts
  cli.ts → add.ts → agents.ts
  cli.ts → add.ts → installer.ts
```

**关键技巧：**

- **先看 import 语句**：每个文件顶部 import 了什么，直接告诉你它依赖谁
- **先看 export 语句**：每个文件对外暴露了什么，直接告诉你它的职责
- **先看类型/接口定义**：数据结构比算法更容易理解，先搞懂"数据长什么样"

**这遍的输出：**
- 一张目录职责表（每个目录一句话）
- 一张模块依赖关系图（文本箭头即可）
- 核心类型/接口的简单定义

## 第四遍：主链路（怎么跑的？）

**目标：追踪一条完整的执行路径，从用户输入到最终输出。**

### 方法：向后追踪法

```
选一个最典型的用户操作，从入口跟到底。

入口函数
  → 它调用了谁？
    → 被调用的又调用了谁？
      → ...直到数据落地或返回给用户

每层记录：
  - 函数名和文件:行号
  - 输入参数是什么
  - 返回值是什么
  - 核心逻辑（一句话）
  - 这一层做了什么决策/判断
```

### 具体做法

```
1. 找到入口（比如 CLI 命令的 handler）
2. 列出这个函数里所有的函数调用
3. 先追踪"主分支"（最常见的执行路径），跳过错误处理
4. 对每个关键调用，进去看函数签名和核心逻辑
5. 画出一条从入口到出口的完整链路
```

### 输出格式

```
用户操作：npx skills add vercel-labs/agent-skills

执行链路：
1. bin/cli.mjs:14 → import dist/cli.mjs，启动 Node.js
2. cli.ts:916 → main() 匹配到 "add" 命令
3. cli.ts:918 → 调用 parseAddOptions() 解析参数
4. cli.ts:919 → 调用 runAdd(source, options)
5. add.ts:942 → parseSource(source) 解析为 GitHub URL
6. add.ts:1041 → cloneRepo(url) 克隆到临时目录
7. add.ts:1045 → discoverSkills(tempDir) 扫描 SKILL.md
8. add.ts:1266 → promptForAgents() 选择安装到哪些 agent
9. add.ts:1495 → installSkillForAgent() 逐 skill 逐 agent 安装
10. add.ts:1623 → addSkillToLock() 写入锁文件
```

**红线：**
- 不要在读完主线之前跳到分支
- 不要同时追踪多条路径
- 主线没走完前，不要纠结某个函数的内部细节

## 第五遍：深度拆解（为什么这样设计？）

**对每个关键模块，从六个维度拆解：**

### 六维分析框架

对每个重要模块/文件，回答这六个问题：

```
1. 【是什么】
   → 这个模块叫什么？在项目中的角色是什么？
   → 类比：它像一个什么日常事物？

2. 【讲什么】
   → 核心功能是什么？输入什么、输出什么？
   → 有哪些关键函数/方法？每个做什么？

3. 【怎么用】
   → 外部怎么调用它？需要什么参数？
   → 有没有使用示例？在项目中谁调用了它？

4. 【技术技巧】
   → 用了什么算法、数据结构、设计模式？
   → 有哪些"原来还可以这样写"的巧妙实现？
   → 有哪些值得学习的编码风格或命名约定？

5. 【优点 & 缺点】
   → 这个设计好在哪里？解决了什么具体问题？
   → 有什么局限？什么场景下不适用？
   → 作者做了什么取舍？为什么这样取舍？

6. 【实战注意】
   → 如果要修改这个模块，要注意什么？
   → 有哪些隐藏的坑？有哪些隐式约定？
   → 怎么验证你的修改没有破坏原有功能？
```

### 输出示例

```
模块：add.ts [add.ts:895-1793]

【是什么】skills-cli 的安装命令核心实现。类比：npm install 的主逻辑。

【讲什么】
  - runAdd(source, options) → 解析来源、发现 skill、安装到 agent
  - parseAddOptions(args) → 解析命令行参数
  - handleWellKnownSkills() → 处理 well-known 来源
  - promptForAgents() → 交互式选择 agent
  - promptForFindSkills() → 安装后推荐安装 find-skills

【怎么用】
  内部被 cli.ts:919 调用。外部不可直接调用，通过 CLI 入口。

【技术技巧】
  - Blob 快速安装：对 allowlist org 跳过 git clone，直接用 GitHub API 拉文件
    [add.ts:1017-1033]
  - 隐私检查并行化：安装开始前就启动 isPrivate() Promise，遥测时不阻塞
    [add.ts:948-956]
  - 安全门控：openclaw 来源需显式传 --dangerously-accept-openclaw-risks
    [add.ts:958-975]

【优点 & 缺点】
  优点：安装流程考虑周全（多来源、多 agent、多模式）
  缺点：函数过长（~1900 行），runAdd 职责过多（解析+安装+锁+遥测）
  取舍：宁可一个长文件也不过度抽象（符合项目定位）

【实战注意】
  - 修改安装逻辑时必须同时考虑 symlink/copy/blob 三种模式
  - 锁文件版本升级是破坏性的（旧版本直接 wipe）
  - 遥测仅对公开仓库上报，修改时注意隐私
```

### 输出结构

文档分三层，用户按需阅读：

```markdown
## 第一层：快速概览（5 分钟）
### 一句话概括

### 完整主链路（每步带文件:行号）
### 模块六维分析（每个关键模块一张表）
### 核心数据结构详解
### 关键设计模式及原因

## 第三层：实战指南（动手做）
### 3 个从易到难的练习
### 常见修改场景及注意事项
### 测试怎么跑、怎么加新功能
```

### 快速概览模板

```markdown
## [项目名] 快速概览

### 一句话概括
[项目是做什么的，10 个字以内]

### 解决的痛点
用户原来怎么做的 → 有什么问题 → 这个项目怎么解决的

### 架构图
[文本箭头图]

### 主链路（最简版）
1. 入口 → 2. 解析 → 3. 核心处理 → 4. 输出

### 最值得学的 3 个点
1. [设计/技巧] — [文件:行号] — [一句话说明为什么好]
2. ...
3. ...
```

### 深度拆解模板

对每个模块套用六维框架，格式见"第五遍"。

### 禁止事项

- 禁止 "TODO"、"大概"、"应该"、"可能是"
- 禁止 "类似 xxx 的实现" 而不给具体引用
- 禁止没有行号的概括性描述
- 禁止只有"是什么"没有"为什么"

## 自检清单

```
□ 第一遍（鸟瞰）：不看源码能否说清这个项目是什么？
  → 说不清 → 回去读 README + package.json

□ 第二遍（骨架）：能否画出模块间的依赖关系？
  → 画不出 → 回去看每个文件的 import/export

□ 第三遍（主链路）：能否从入口到出口完整走一遍？
  → 走不通 → 有函数调用你没追踪到

□ 第四遍（深度）：每个关键模块都做了六维分析？
  → 漏维度 → 补充缺失的分析角度

□ 第五遍（输出）：文档分了三层？
  → 没分层 → 不同读者需要不同深度

□ 每个结论都有文件:行号证据？
  → 没行号 → 不是理解，是猜测

□ 有没有"大概""应该""可能是"？
  → 有 → 回去读代码，读到确定为止

□ 核心设计的"为什么"是否解释了具体约束？
  → 没解释 → 你还没真正理解设计决策
```

## 红旗信号

| 你的行为 | 为什么错了 |
|----------|-----------|
| 读了 3 个文件还不清楚项目干什么 | 没先看 README 和入口文件 |
| 在读第 5 层嵌套，但入口函数还没读完 | 在追分支，不是主线 |
| 拆解文档有"大概""应该""可能是" | 在猜，不是在读 |
| 花了 10 分钟还在同一个文件里 | 你逐行读，没有带着问题找答案 |
| 跳过 package.json 直接读源码 | 错过了最关键的结构信息 |
| 只写"是什么"不写"为什么" | 你只是在描述，不是在分析 |
| 文档只有技术细节没有实战指导 | 忽略了"学了怎么用" |
| 所有模块平均用力 | 不分主次，没有重点 |

## 常见借口

| 借口 | 真相 |
|------|------|
| "我先大致扫一遍再说" | 没有目标的扫描 = 读了就忘。先定义问题。 |
| "这个项目很简单，不用看文档" | package.json 有入口、依赖、脚本，信息密度最高 |
| "我先看懂这个工具函数" | 先理解它在主线中的角色，再深入细节 |
| "源码太长，我概括一下" | 概括没有引用 = 猜测。宁可范围缩小，不证据打折。 |
| "我看过类似的项目" | 每个项目有自己的设计决策。预设会忽略关键差异。 |
| "用户只需要知道怎么用" | 用户深层需求是"理解原理后自己能改"。给鱼不如给渔。 |
| "写太详细用户看不完" | 分层输出解决这个问题：概览 5 分钟，深度 30 分钟，各取所需。 |

## 用户想要什么？— 教学优先级

不同用户需要不同的教学重点。根据第一步的确认，调整输出重心：

```
用户要"理解架构"
  → 重点：第二遍（骨架）+ 第三遍（主链路）
  → 略读：模块内部细节
  → 输出：架构图 + 设计模式 + 模块职责

用户要"复用功能"
  → 重点：第三遍（主链路）+ 第四遍（六维分析）
  → 略读：无关模块
  → 输出：API 文档 + 调用示例 + 注意事项

用户是技术新手
  → 重点：每一步都加比喻、类比、白话解释
  → 每个概念第一次出现时解释
  → 输出：教学文档 + 可执行练习

用户要二次开发
  → 重点：第四遍（六维分析）+ 扩展点 + 代码约定
  → 略读：不需要改的模块
  → 输出：修改指南 + 影响面分析 + 测试方式
```

## 后续路径

拆解完成后，根据用户需求走不同路径。以下方法论已内嵌，无需额外技能。

---

### 路径 A：拆解后要自己实现

**铁律：先设计后编码，未经确认不写代码。**

```
1. 理解意图
   - 问清楚：做什么、不做什么、验收标准
   - 一次只问一个问题

2. 设计方案
   - 提出 2-3 种方案，对比权衡，给出推荐
   - 确认模块划分：每个文件一个职责，接口清晰
   - 逐部分展示设计，每部分获得确认后再继续

3. 输出实现计划
   - 列出要创建/修改的文件及职责
   - 分解为原子任务（每个 2-5 分钟）
   - 每步遵循：写测试 → 看它失败 → 写实现 → 通过测试 → 提交
   - 每个步骤包含完整代码，不允许 "TBD"、"类似上面"
```

---

### 路径 B：拆解中发现 Bug

**铁律：未找到根因之前，不修复任何问题。**

```
1. 定位根因
   - 仔细读取错误信息/堆栈，不跳过任何行
   - 确认能否稳定复现
   - 检查最近变更（git diff、最近提交）
   - 追踪数据流：值从哪里来→经过什么变换→到哪里出错
   - 在多层系统中逐层加诊断日志，确定哪一层出问题

2. 模式分析
   - 找代码库中相似的工作代码做对比
   - 列出所有差异，不假设"这个不影响"
   - 理解被依赖的组件、配置、环境假设

3. 验证假设
   - 每次只验证一个假设
   - 做最小改动来验证，不要同时修多个东西
   - 验证不通过 → 换假设，不叠加修复

4. 实施修复
   - 先写最小复现测试用例
   - 修复根因，不是修复症状
   - 验证修复后原测试和新增测试都通过
```
